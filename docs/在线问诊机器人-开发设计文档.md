## 一、为什么改，改成什么

### 1.1 现状诊断：不是「太大」，是「太浅」

原判断「智慧医药查询系统太大了」需要修正。实测数据不支持「太大」：

| 指标 | 实测值 | 典型个人项目 | 结论 |
|---|---|---|---|
| 后端代码量 | 2653 行 / 53 文件 | 3000–10000 行 | **偏小** |
| HTTP 端点 | 31 个 | 20–50 | 正常 |
| 数据库表 | 11 张（3 张是死表） | 8–15 | 正常 |
| Service 层 | 6 个 / 466 行 | — | 偏薄 |

真正的问题是 **8 个模块的深度完全一样**，且都停在 CRUD：

| Service | 行数 | 业务方法数 | 真正含业务逻辑的方法 |
|---|---:|---:|---|
| `FeedbackService.java` | 36 | 3 | 1（`submit` 只多一行 `setStatus(0)`） |
| `DoctorService.java` | 45 | 5 | 1（只有 `search` 拼条件，其余 4 个是 `return xxxMapper.yyy()` 一行） |
| `MedicineService.java` | 93 | 6 | 3（`search` / `searchByKeywords` / `getById` 的 status 过滤） |
| `AuthService.java` | 132 | 3 | 3（登录 / 注册 / 验证码） |
| `AiDoctorService.java` | 136 | **1** | 1（`chatStream`；另有 2 个 private 辅助方法） |
| `IllnessService.java` | 156 | 9 | 3（`search` / `searchByKeywords` / `fillCategoryNames`） |

> 注：方法数只统计 public 业务方法，不含构造器。`AiDoctorService` 136 行只有 **1 个** public 方法，是这个表里最极端的一行 —— 一个方法干了存消息、取历史、检索、调模型、假流式、错误处理六件事。

31 个端点的分布是 **12 GET / 9 POST / 7 PUT / 3 DELETE** —— 本质是同一套 CRUD 换了 8 个名词。
**全部业务深度压在 2 个文件**：`integration/ai/KnowledgeRetrievalService.java`（200 行）+ `integration/ai/DashScopeClient.java`（151 行）。其余 1800 行是脚手架。

### 1.2 病根在领域，不在代码

「医药查询」这个领域对 Java 后端面试天然不友好：

| 面试考察点 | 查询系统能给什么素材 |
|---|---|
| 状态怎么变 | 没有状态。疾病/药品只有 `status` 上下架，是一次赋值，不是状态机 |
| 并发怎么正确 | 没有并发争用。读多写少、无库存、无抢单 |
| 失败怎么收场 | 无跨表写、无补偿、无重试语义 |
| 一致性怎么保证 | 只有一个 `illness_medicine_rel` 关联表，插两条就完了 |

而同一个人的 `stock-assistant` 项目里已经有的东西（库存扣减、乐观锁、预警状态机），本项目的领域**给不了**。

### 1.3 决策：从「查询系统」改成「在线问诊机器人」

保留已建成的知识库与 RAG 能力，把业务主线从「查」改成「诊」—— 一次问诊就是一个有生命周期、有状态流转、有并发可能、有失败分支的业务对象。

**改造前后对比**：

| 维度 | 改造前（查询系统） | 改造后（在线问诊） |
|---|---|---|
| 核心实体 | illness / medicine / doctor（只读字典） | + consultation（问诊单，有状态） |
| 核心动作 | GET 列表 / GET 详情 | 发起问诊 → 多轮对话 → 完结 → 产小结 → 超时关闭 |
| 状态 | 无 | 4 态机（进行中 / 已完成 / 已取消 / 超时关闭） |
| 并发点 | 无 | 并发完结（患者 vs 定时任务）、重复发起、小结并发生成 |
| 事务边界 | 无 | 完结时写结论 + 改状态 + 写审计，三写一事务 |
| 失败分支 | 无 | AI 不可用 → 降级并告知；小结生成失败 → 可重试；超时 → 自动关闭 |
| 角色 | 用户 / 管理员 | 用户 / 管理员（**不变**） |

### 1.4 保留、改造、新增的边界

写代码前必须先划清这条线，否则会推倒重来。

| 处理 | 对象 | 理由 |
|---|---|---|
| **完全保留** | `security/` 全部、`common/` 全部、`config/SecurityConfig`+`MyBatisPlusConfig`+`MyMetaObjectHandler` | 认证链路、统一响应、异常映射已修到位，动它没有收益 |
| ✅ 保留（收窄） | `illness/`、`medicine/` 的**数据层**（entity / mapper / service） | RAG 的知识底座。Controller 已删，用户侧不再有浏览入口 |
| **完全保留** | `integration/ai/KnowledgeRetrievalService`、`DashScopeClient` | 检索与模型调用已修复过（相关度重排、错误语义），是项目最有价值的部分 |
| ✅ 已完成 | `module/ai_doctor/` → 并入 `consultation` 域 | `AiChatRecord` + `AiChatRecordMapper` 迁到 `consultation.entity` / `consultation.mapper`；Controller / Service 已删 |
| ✅ 已完成 | `module/consultation/` 整个模块 | 问诊单、状态机、小结生成、超时任务，另有 `triage/` 规则引擎 |
| ✅ 已完成 | `frontend/src/pages/user/ConsultationPage.vue` | 问诊主界面。**不是**从 `AiDoctorPage.vue` 改造，而是全重写（旧的只有单轮对话、无会话列表、无小结） |
| ✅ 保留 | `sys_user.role_status` / `ai_chat_record.role` | 纯 AI 不需要医生角色，两处原样不动。`sys_doctor` 已删表 |
| ❌ 已废弃 | `dashboard/` 整个模块 | 数据大屏与问诊主线无关，连同 `DashboardPage.vue` 与 echarts 依赖一起删。计数改由 `module/stats/PublicStatsController` 提供 |
| ❌ 已废弃 | `feedback/` 整个模块 | 冻结不如删干净，连同 `feedback` 表一起移除 |

### 2.4 已经修好的东西（不要在改造中回退）

改造过程中最容易踩的坑是把这些改回去。

| 已修复项 | 落点 | 为什么不能回退 |
|---|---|---|
| 认证上下文传递 | `JwtAuthenticationFilter` 里 `request.setAttribute("userId", userId.intValue())` | 只 `setDetails` 不 `setAttribute` 时，`@RequestAttribute` 恒为 null，个人中心全部 401 |
| 时间字段自动填充 | `config/MyMetaObjectHandler.java` | 没有它 `create_time` 全写 NULL，DDL 的 `DEFAULT CURRENT_TIMESTAMP` 救不了 MyBatis-Plus 的显式 null |
| 会话历史上限 | `AiDoctorService.getSessionHistory` 用 `orderByDesc(createTime).orderByDesc(id).last("LIMIT 20")` 再 `reverse` | 原来用 `orderByAsc(...LIMIT 20)`，长会话永远只看最早 20 条 |
| 浏览量自增 | `IllnessService.incrViewCount` + `@CacheEvict`，从 `getById` 里拆出来 | 原来写在 `@Cacheable` 方法体内，缓存命中就永不增长 |
| 分类名回填 | `IllnessService.fillCategoryNames` 用 `selectBatchIds` | 原来是循环 `selectById`，9 条记录 11 条 SQL |
| 检索相关度 | `KnowledgeRetrievalService` 的 `Scored<T>` + 词长加权 | 原来按 `LinkedHashSet` 插入序截断 Top3，与相关度无关 |
| AI 错误语义 | `common/exception/AiServiceException` + `DashScopeClient.translate` | 原来 429/401/403 全被 catch 成一句中文兜底，HTTP 200，故障被伪装成正常回答 |
| HTTP 状态码 | `GlobalExceptionHandler.handleBusinessException` 返回 `ResponseEntity` | 原来恒 200，前端 `error.response?.status === 401` 永不成立，「密码错误」不显示 |
| 401 vs 403 | `SecurityConfig` 的 `authenticationEntryPoint` / `accessDeniedHandler` | 默认是 403，前端靠 401 跳登录，等于不跳 |
| 缓存 null | `@Cacheable(unless = "#result == null")` | 不加则查不存在的 id 直接 500 |
| SSE 气泡对比度 | 原 `AiDoctorPage.vue` 的 `.message.assistant .msg-content` | 修复前白字浅灰底，对比度 1.10:1。v2.0 该页已删，样式迁到 `ConsultationPage.vue` |

## 三、目标定位与产品边界

### 3.1 一句话定位

> 一个**有状态的纯 AI 在线问诊机器人**：患者发起问诊 → AI 结合医学知识库多轮追问 → 产出结构化小结 → 高危时给出紧急就医提示并置顶标识 → 超时自动关闭。全程可追溯、可审计。

**决策记录**：产品形态定为**纯 AI，不做人工兜底**（用户 2026-11-05 决策）。这意味着没有医生角色、没有待接诊队列、没有抢单并发。代价与补偿见 3.5。

### 3.2 要做（In Scope）

| 能力 | 说明 |
|---|---|
| 发起问诊 | 填写主诉，创建问诊单，状态 `进行中` |
| 多轮对话 | SSE 流式，携带最近 20 轮历史 + 知识库检索结果 |
| **实时分诊**（v2.0 新增） | 每条消息进来先用 `TriageRuleEngine` 做一次纯内存规则匹配，命中高危时**在 SSE 第一帧**就带 `triageSeverity=2` 与 `redFlags`，前端横幅先于 AI 第一个字出现 |
| 结构化小结 | 会话结束时由 AI 产出 **12 个字段**：主诉 / 病程 / 症状 / 疑似方向 / 建议科室 / 科室理由 / 居家护理 / 用药提示 / 危险信号 / 严重程度 / 严重程度理由 / 免责声明 |
| 高危标识 | 两处：① **实时**——规则引擎命中即弹红色横幅，不等小结；② **回顾**——AI 在小结里判 `severity=2` 时问诊单打标，侧栏列表显示红色警告图标 |
| 完结 / 取消 | 患者可主动完结或取消；完结时自动生成小结作为 `conclusion` |
| 超时关闭 | 30 分钟无活动自动关闭，定时任务扫描 |
| 免责声明 | 所有 AI 输出强制附带，前端固定位置展示，不依赖模型自己说 |

### 3.3 不做（Out of Scope）

明确不做，防止范围蔓延：

- ❌ **人工医生接诊 / 待接诊队列 / 抢单**（本次决策排除）
- ❌ 处方开具（法律风险，不是技术问题）
- ❌ 支付 / 订单
- ❌ 视频 / 语音问诊
- ❌ 药品库存与配送
- ❌ 电子病历对接（HIS / EMR）
- ❌ 多租户 / 多医院 SaaS

### 3.4 角色定义（只有两个）

| 角色 | `role_status` | 能力 |
|---|---|---|
| 患者 | `0` | 发起问诊、对话、查看自己的问诊历史、完结/取消、删除自己的记录 |
| 管理员 | `1` | 查看审计日志（`/api/v1/admin/operation-logs`）。**无数据大屏、无用户管理页**——两者已随模块删除 |

**`sys_user.role_status` 不需要改取值域**，`JwtAuthenticationFilter` 的三元表达式也**不用动**。这是纯 AI 方案省下的第一处改动。

`sys_doctor` 表在 v2.0 **已删除**。「建议就诊科室」改由 `TriageRuleEngine` 的关键词映射 + 模型判断给出，不再依赖医生表。

### 3.5 纯 AI 方案的技术取舍（必须诚实面对）

砍掉人工兜底后，**丢掉了哪些技术点**，以及**用什么补回来**：

| 丢失的技术点 | 为什么丢 | 补偿方案 |
|---|---|---|
| 医生抢单的乐观锁并发 | 没有第二方参与 | **改用「并发完结」**：患者点完结 + 定时任务判超时同时打同一张单，靠 `@Version` + `WHERE status=0` 条件更新保证只有一个成功。并发场景真实存在，只是对手从「另一个医生」变成「定时任务」 |
| 细粒度鉴权（是不是本人的单） | 患者查自己的单仍需鉴权 | **保留**。`ConsultationGuard.isOwner` 依然必要，只是去掉 `isAssignedDoctor` |
| 三角色 RBAC | 只有患者/管理员 | **降级为两角色**，但在 `SecurityConfig` 里新增 `/api/v1/consultations/**` 的归属校验规则，仍有权限分层可讲 |
| 待接诊队列的状态流转 | 无队列 | **改成「小结生成」的状态流转**：`进行中 → 生成中 → 已完成`，小结生成是异步的，同样有中间态 |

**坦白说明**：纯 AI 方案下，本项目的并发点从 2 个（抢单 + 完结）降到 1 个（完结 vs 超时）。这在面试里仍可讲——「定时任务和用户操作同时改一行数据」是真实的生产问题，比虚构的抢购场景更贴合本项目——但确实弱于人工兜底方案。这个取舍是你做的决定，文档如实记录。

### 3.6 一句话总结

**从「查资料的网站」变成「会追问、会记录、会收尾的问诊单系统」。** 深度来自状态机和数据一致性，不来自角色数量。

## 四、领域模型设计

### 4.1 核心实体关系

```
sys_user (患者/管理员)
   │
   └─1:N─> consultation (问诊单)  ← 本次新增的核心
              │
              └─1:N─> ai_chat_record (消息，复用现有表)

illness / medicine / doctor  ← 保留为 RAG 知识底座与「建议科室」参考，不参与状态流转
```

**纯 AI 方案下没有 `doctor_id` 外键**。v2.0 进一步把 `sys_doctor` 整张表删掉——医生数据本来就只用于回答「建议挂什么科」，而这件事 `TriageRuleEngine` 做得更准且零 IO。

### 4.2 新增表：`consultation`

```sql
CREATE TABLE `consultation` (
    `id`              INT          NOT NULL AUTO_INCREMENT COMMENT '问诊ID',
```

**相比人工兜底方案的变化**：

| 变化 | 原因 |
|---|---|
| 删除 `doctor_id` 与 `idx_doctor_status` | 没有医生接诊 |
| 新增 `summary_status` | 补回一个可观测的中间态（见 3.5 的补偿方案） |

**设计要点**：

| 字段 | 为什么这么设计 |
|---|---|
| `session_id` UNIQUE | 幂等键。前端重试/双击不会创建两张问诊单，靠 `DuplicateKeyException` 兜住 |
| `version` | 乐观锁。并发完结（患者点完结 + 定时任务判超时同时发生）必须有版本保护 |
| `last_active_at` 独立于 `update_time` | `update_time` 会被任何 UPDATE 刷新（含状态变更）；超时判定要看的是「最后一条消息时间」，语义不同 |
| `status` 用 TINYINT 不用 ENUM | 与现有 11 张表风格一致；修改枚举值不用 DDL |
| `ai_summary` 存 JSON 字符串 | 结构可能演进（加字段不需改表）。**代价**：无法 SQL 查询内部字段，如需统计要另建宽表 |
| `summary_status` 与 `status` 分开 | 小结生成是异步的，可能失败重试。`status=1 已完成` 但 `summary_status=3 生成失败` 是合法状态，要求它们同步会让状态机纠缠 |

## 五、状态机设计

### 5.1 状态定义

**问诊单主状态**：

| 值 | 名称 | 含义 | 终态 |
|---|---|---|---|
| `0` | `IN_PROGRESS` | 进行中（AI 对话中） | 否 |
| `1` | `COMPLETED` | 已完成（已产出结论） | **是** |
| `2` | `CANCELLED` | 已取消（患者主动取消） | **是** |
| `3` | `TIMEOUT` | 超时关闭（30 分钟无活动） | **是** |

**小结状态**（`summary_status`，与主状态正交）：

| 值 | 名称 | 含义 |
|---|---|---|
| `0` | `NONE` | 未生成（对话进行中） |
| `1` | `GENERATING` | 生成中（异步任务已提交） |
| `2` | `DONE` | 已生成（`ai_summary` 非空） |
| `3` | `FAILED` | 生成失败（可重试） |

**为什么把小结状态独立出来**：小结生成依赖外部 AI 服务，可能超时、限流、返回畸形 JSON。如果把它塞进主状态，会出现「状态=生成中但对话还能继续吗」这类纠缠问题。拆开后语义清晰：**对话归对话，小结归小结**，`status=1 已完成` 配 `summary_status=3 生成失败` 是完全合法的状态，用户可以点「重新生成」。

`severity` 是**第三个正交维度**：

| 值 | 含义 | 副作用 |
|---|---|---|
| `0` | 低风险 | 无 |
| `1` | 中风险 | 无 |
| `2` | 高危 | 前端置顶红色横幅「请立即就医或拨打 120」；管理端看板可筛出 |

> 设计辨析：`severity` 不做成状态，因为它不参与生命周期流转 —— 一张已完成的单也可能是高危，一张进行中的单可能一直低危。做成状态会导致「高危的已完成单」无法表达。

### 5.2 合法转移表

| 当前状态 | 目标状态 | 触发者 | 条件 |
|---|---|---|---|
| `IN_PROGRESS` | `COMPLETED` | 患者（调完结接口） | 必须已生成小结，或完结时同步生成 |
| `IN_PROGRESS` | `CANCELLED` | 患者 | 无（任何时刻可取消） |
| `IN_PROGRESS` | `TIMEOUT` | 定时任务 | `last_active_at` 早于 `now - 30min` |
| `COMPLETED` | * | — | 拒绝：`IllegalStateTransitionException` → HTTP 409 |
| `CANCELLED` | * | — | 拒绝 |
| `TIMEOUT` | * | — | 拒绝 |

**没有任何「终态 → 非终态」的边**。这是刻意的：问诊结论一旦产出就是医疗记录，不允许复活改写。

> 如果后续需要「重新问诊」，正确做法是**新建一张问诊单**（新 `session_id`），而不是复用旧的。这样历史留痕完整。

**小结状态转移**（独立的表，不与主状态混）：

| 当前 | 目标 | 触发者 |
|---|---|---|
| `NONE` | `GENERATING` | 完结接口 / 手动触发 |
| `GENERATING` | `DONE` | 异步任务成功 |
| `GENERATING` | `FAILED` | 异步任务异常（超时/限流/解析失败） |
| `FAILED` | `GENERATING` | 患者点「重新生成」 |

**`DONE` 是终态**：已生成的小结不能重生成，避免用户反复覆盖医疗记录。要换结论只能新建问诊单。

### 5.3 状态机落点

新建 `module/consultation/statemachine/ConsultationStateMachine.java`：

```java
public final class ConsultationStateMachine {

    /** 主状态合法转移表：只有 IN_PROGRESS 能出去 */
    private static final Map<Integer, Set<Integer>> ALLOWED = Map.of(
        ConsultationStatus.IN_PROGRESS, Set.of(
            ConsultationStatus.COMPLETED,
            ConsultationStatus.CANCELLED,
            ConsultationStatus.TIMEOUT
        )
    );

    /** 小结状态合法转移表 */
    private static final Map<Integer, Set<Integer>> SUMMARY_ALLOWED = Map.of(
        SummaryStatus.NONE,       Set.of(SummaryStatus.GENERATING),
        SummaryStatus.GENERATING, Set.of(SummaryStatus.DONE, SummaryStatus.FAILED),
        SummaryStatus.FAILED,     Set.of(SummaryStatus.GENERATING)
    );

    public static void checkTransition(int from, int to) {
        if (!ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
            throw new IllegalStateTransitionException("问诊状态", from, to);
        }
    }

    public static void checkSummaryTransition(int from, int to) {
        if (!SUMMARY_ALLOWED.getOrDefault(from, Set.of()).contains(to)) {
            throw new IllegalStateTransitionException("小结状态", from, to);
        }
    }

    public static boolean isTerminal(int status) {
        return status != ConsultationStatus.IN_PROGRESS;
    }
}
```

**为什么用静态类而不是 Spring Bean**：状态机是无状态的纯函数，不需要注入。做成 Bean 只会让测试变麻烦（要起 Spring 上下文）。

**为什么不用 Spring StateMachine**：引入一个框架只为一个 4 态机，代价远大于收益。4 个状态、3 条边、无嵌套状态、无并发区域，手写转移表 30 行就完了。引框架是为了解决复杂度，不是为了炫。面试时「为什么不用 Spring StateMachine」是个可回答的问题。

### 5.4 状态流转图

**主状态**：

```
                    ┌──────────────┐
                    │  IN_PROGRESS │
                    │      0       │
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        │ 患者完结          │ 患者取消          │ 定时任务
        │                  │                  │ 30min 无活动
        ▼                  ▼                  ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  COMPLETED   │   │  CANCELLED   │   │   TIMEOUT    │
│      1       │   │      2       │   │      3       │
└──────────────┘   └──────────────┘   └──────────────┘
   （终态）             （终态）             （终态）
```

**小结状态**（独立演进，可与主状态并行）：

```
   ┌───────┐  完结触发   ┌────────────┐  成功  ┌──────┐
   │ NONE  │───────────>│ GENERATING │───────>│ DONE │
   │   0   │            │     1      │        │  2   │（终态）
   └───────┘            └─────┬──────┘        └──────┘
                              │ 失败
                              ▼
                        ┌──────────┐  重新生成
                        │  FAILED  │─────────┐
                        │    3     │<────────┘
                        └──────────┘
```

**关键：两个状态机互不阻塞**。用户可以在一张 `summary_status=FAILED` 的单上看到「重新生成」按钮，而不影响 `status=COMPLETED` 的既成事实。

### 5.5 并发下的状态安全（纯 AI 方案的核心考点）

纯 AI 没有医生抢单，但**并发点仍然真实存在**：

| 场景 | 时序 | 不加保护的结果 | 保护手段 |
|---|---|---|---|
| 完结 vs 超时 | 患者 09:59:59 点完结，定时任务 10:00:00 扫到该单 | 两者都成功，最终状态取决于谁后写，可能「已完成」被改成「超时关闭」 | `WHERE status = 0` 条件更新 + `@Version`，只有一个影响行数=1 |
| 双击完结 | 用户手抖点两下 | 第二次抛 409 或静默成功，`conclusion` 被写两遍 | 条件更新，第二次影响行数=0 → 抛 `IllegalStateTransitionException` |
| 小结并发生成 | 用户点两次「重新生成」 | 两个异步任务同时跑，后完成的覆盖先完成的 | `summary_status` 条件更新（`WHERE summary_status IN (0,3)`），只有一个能进 `GENERATING` |
| 重复创建 | 前端重试 | 两张问诊单 | `uk_session` 唯一索引 |

**实现示例（完结）**：

```java
@Transactional
public void complete(Integer id, Integer patientId, String conclusion) {
    // 1. 先做内存态校验，快速失败（不改库）
    var c = consultationMapper.selectById(id);
    if (c == null) throw BusinessException.notFound("问诊不存在");
    if (!patientId.equals(c.getPatientId())) throw BusinessException.forbidden("无权操作");
    ConsultationStateMachine.checkTransition(c.getStatus(), ConsultationStatus.COMPLETED);

    // 2. 条件更新，数据库层兜底并发
    int affected = consultationMapper.update(null,
        new LambdaUpdateWrapper<Consultation>()
            .eq(Consultation::getId, id)
            .eq(Consultation::getStatus, ConsultationStatus.IN_PROGRESS)  // ← 关键
            .eq(Consultation::getVersion, c.getVersion())                  // ← 乐观锁
            .set(Consultation::getStatus, ConsultationStatus.COMPLETED)
            .set(Consultation::getConclusion, conclusion)
            .set(Consultation::getClosedAt, LocalDateTime.now())
            .set(Consultation::getVersion, c.getVersion() + 1));

    // 3. 影响行数 0 = 被别人抢先改了
    if (affected == 0) {
        throw new IllegalStateTransitionException("问诊已被完结或关闭，请刷新后重试");
    }
}
```

**为什么第 1 步和第 2 步都要做**：第 1 步给用户友好提示（速度快、报错准），第 2 步防并发（数据库原子性）。只有第 1 步会在并发下失效；只有第 2 步会给用户报「状态不对」而说不出所以然。

### 6.2 模块职责边界

| 类 | 职责 | 不该做的事 |

| `ConsultationMessageService` | 消息落库、取历史、更新 `last_active_at`、驱动 SSE | **不管状态机** |

| `ConsultationGuard` | SpEL 权限判定（是否单主） | 不查业务数据以外的东西 |

**为什么把「调 AI」和「存消息」拆开**：`AiDoctorService` 现在一个类 136 行、只有 1 个 public 方法，却干了 6 件事（存消息、取历史、检索、调模型、假流式、错误处理）。拆开后每个类只对一个变化源负责：

| 变化源 | 影响哪个类 | 不影响 |
|---|---|---|
| AI 模型换了 / SDK 升级 | `DashScopeClient` | 状态机、消息存储 |
| 小结 JSON 结构变了 | `ConsultationSummaryService` | 对话链路 |
| 状态机加一个状态 | `ConsultationStateMachine` | AI 调用 |
| SSE 改成 WebSocket | `ConsultationMessageService` + `AsyncConfig` | 状态机、小结 |
| RAG 缓存策略变了（TTL / 键格式） | `DashScopeClient` | 状态机、消息存储、小结 |

这就是拆分带来的实际收益：**改一处不会牵动全部**。

### 6.3 线程模型改造

**现状问题**（`AiDoctorService.chatStream`，第 70 行）：

```java
new Thread(() -> { ... }).start();
```

裸线程，无池化、无上限、无拒绝策略。100 个并发问诊就是 100 个平台线程，且 `Thread.sleep(20)` 空转。

**改造方案**：新建 `config/AsyncConfig.java`，**两个池，用途不同**：

```java
@Configuration
public class AsyncConfig {

    /** SSE 流式输出：IO 密集，线程会被 sleep 与网络写阻塞 */
    @Bean("sseExecutor")
    public ThreadPoolTaskExecutor sseExecutor() {
        var e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(8);
        e.setMaxPoolSize(32);
        e.setQueueCapacity(64);
        e.setThreadNamePrefix("sse-");
        // 队列满直接拒绝，由调用方转成 SSE error 事件
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        e.initialize();
        return e;
    }

    /** 小结生成：CPU 极轻但耗时长（等 AI），小池即可 */
    @Bean("summaryExecutor")
    public ThreadPoolTaskExecutor summaryExecutor() {
        var e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(2);
        e.setMaxPoolSize(4);
        e.setQueueCapacity(32);
        e.setThreadNamePrefix("summary-");
        e.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        e.initialize();
        return e;
    }
}
```

**为什么分成两个池**：小结生成要等 AI，一次可能 10–30 秒。如果和 SSE 共用一个池，几个慢小结就能把长连接挤出队列，导致用户对话被拒。分池隔离故障域。

**关键约束**：
- 线程池满时**必须**抛出可识别异常，转成 SSE error 事件或 `summary_status=FAILED`，而不是让请求挂死
- `SseEmitter` 的 `onTimeout` / `onCompletion` / `onError` 都要注册清理逻辑，否则线程与连接双泄漏
- SSE 超时保持 `120000L`（2 分钟），但必须与 nginx `proxy_read_timeout` 对齐（见 11.3）

### 6.4 实体与常量

现有实体的风格是**纯 Lombok `@Data` + 无枚举**（`status` 是 `Integer`）。新增模块照此风格，但**把魔法数字收敛到常量类**：

```java
// module/consultation/entity/ConsultationStatus.java
```

### 6.5 小结 JSON 契约

`ai_summary` 存 JSON 字符串。结构必须固定，否则前端没法渲染、后端没法解析。

```json
{
  "chiefComplaint": "最近三天咳嗽发烧，最高38.5度",
  "possibleDirections": ["上呼吸道感染", "病毒性感冒"],
  "suggestedDepartments": ["呼吸内科", "发热门诊"],
  "medicationHints": ["多饮水休息", "体温超过38.5度可考虑退热药"],
  "severity": 1,
  "severityReason": "有发热但无呼吸困难、无意识改变",
  "redFlags": [],
  "disclaimer": "以上为AI基于知识库生成的参考信息，不能替代医生面诊"
}
```

**字段约束**：

| 字段 | 必需 | 类型 | 兜底 |
|---|---|---|---|
| `chiefComplaint` | 是 | String | 取 `consultation.chief_complaint` |
| `possibleDirections` | 是 | String[] | 空数组 |
| `suggestedDepartments` | 是 | String[] | 空数组 |
| `medicationHints` | 否 | String[] | 空数组 |
| `severity` | 是 | int 0–2 | **解析失败一律为 0** |
| `severityReason` | 否 | String | 空字符串 |
| `redFlags` | 否 | String[] | 空数组；非空时前端置顶告警 |
| `disclaimer` | 是 | String | 后端强制覆盖为固定文案，**不信模型输出** |

**`disclaimer` 必须后端覆盖的原因**：模型可能忘记输出，或输出了但内容不完整。医疗免责声明不能依赖概率。后端收到 JSON 后**无条件覆盖**这个字段。

**解析失败的处理**：

```java
private SummaryVO parse(String raw) {
    try {
        var vo = objectMapper.readValue(raw, SummaryVO.class);
        vo.setDisclaimer(DISCLAIMER_TEXT);           // 强制覆盖
        if (vo.getSeverity() < 0 || vo.getSeverity() > 2) vo.setSeverity(0);
        return vo;
    } catch (Exception e) {
        log.warn("小结 JSON 解析失败，降级为空小结 raw={}", truncate(raw, 200));
        return SummaryVO.empty(DISCLAIMER_TEXT);     // severity 默认 0
    }
}
```

**绝不因为解析失败把 `severity` 设为 2** —— 那会给用户发假的紧急告警，比漏报更糟。

### 7.4 SSE 事件契约

在现有 3 类事件基础上扩展 2 类：

| 事件类型 | 字段 | 说明 | 状态 |
|---|---|---|---|
| `start` | `sessionId` | 流开始 | 现有，已实现 |
| `delta`（chunk） | `chunk` | 文本增量 | 现有，已实现 |
| `error` | `message` / `code` / `retryable` | 错误（429 时 `retryable=true`） | 现有，已实现 |
| **`meta`** | `severity` / `suggestDept` | AI 判定的严重度与建议科室 | **新增** |
| **`end`** | `summarizing` / `summaryStatus` | 流结束，是否触发小结生成 | **新增** |

**为什么把 `severity` 做成独立的 `meta` 事件而不是塞进 `end`**：
- `severity=2` 时前端要**立刻**弹出红色横幅，不能让用户等整段回答吐完
- `meta` 在第一个 chunk 之后就能发（AI 首轮回答里通常已包含风险判断）

```
event:delta
data:{"sessionId":"8f3a1c2e-...","chunk":"您好，"}

event:delta

...

event:delta
data:{"type":"meta","severity":1,"suggestDept":"呼吸内科"}

event:delta
data:{"type":"end","summarizing":false}

```

### 7.6 权限判定实现

用 SpEL + 自定义 Bean，而不是在 Controller 里写 `if`：

```java
@Component("consultGuard")
public class ConsultationGuard {

    private final ConsultationMapper consultationMapper;

    /** 是否问诊单的主人（或管理员） */
    public boolean isOwner(Integer consultationId, Authentication auth) {
        if (auth == null) return false;
        if (isAdmin(auth)) return true;                  // 管理员可查全量
        Integer userId = currentUserId(auth);
        if (userId == null) return false;
        var c = consultationMapper.selectById(consultationId);
        return c != null && userId.equals(c.getPatientId());
    }

    private boolean isAdmin(Authentication auth) {
        return auth.getAuthorities().stream()
                .anyMatch(a -> "ROLE_ADMIN".equals(a.getAuthority()));
    }

    private Integer currentUserId(Authentication auth) { /* 从 auth 取 userId */ }
}
```

用法：

```java
@GetMapping("/{id}")
@PreAuthorize("@consultGuard.isOwner(#id, authentication)")
public Result<ConsultationVO> detail(@PathVariable Integer id) { ... }
```

**为什么不用 `@PreAuthorize("isAuthenticated()")` 就够**：登录只证明「你是谁」，不证明「这张单是你的」。越权读别人的问诊记录是医疗数据泄露，必须查库判归属。

**纯 AI 方案下 Guard 只剩一个方法**（`isOwner`），比人工方案的 `isOwner + isAssignedDoctor` 简单。但这一个方法仍然是必需的，不能省。

### 7.7 HTTP 状态码契约

新增接口沿用现有 `GlobalExceptionHandler` 的映射规则（已在 `main` 上修复）：

| 场景 | HTTP | body.code | 说明 |
|---|---|---|---|
| 正常 | 200 | 200 | |
| 参数校验失败 | 400 | 400 | `@Valid` 不通过 |
| 未登录 | 401 | 401 | `authenticationEntryPoint` 兜底 |
| 非本人 | 403 | 403 | `ConsultationGuard` 判 false |
| 问诊不存在 | 404 | 404 | `BusinessException.notFound` |
| 状态不允许（终态再操作） | **409** | 409 | `IllegalStateTransitionException` |
| 并发冲突（乐观锁失败） | **409** | 409 | 同上，文案不同 |
| AI 服务不可用 | SSE 内 `type=error` | — | **不返回 HTTP 错误**，因为流已开始 |

**最后一条需要特别说明**：SSE 一旦开始推送，HTTP 状态码已经发出去（200）了，后续错误只能通过事件传递。这就是为什么 `sendError` 发 `{"type":"error"}` 而不是 `completeWithError` —— 前端需要拿到可读原因，而不是一个连接中断。

### 8.1 发起问诊

```
患者          前端              ConsultationController    ConsultationService    DB
 │              │                        │                       │              │
 ├─填主诉──────>│                        │                       │              │
 │              ├─POST /consultations───>│                       │              │
 │              │                        ├─参数校验(@Valid)──────>│              │
 │              │                        │                       ├─生成UUID────>│
 │              │                        │                       ├─INSERT──────>│
 │              │                        │                       │   (uk_session)│
 │              │                        │<──Consultation────────┤              │
 │              │<──200 + VO─────────────┤                       │              │
```

**幂等保证**：前端生成 `sessionId` 并复用（重试时带同一个）。若前端未带，后端生成。
**并发保证**：`uk_session` 唯一索引，第二个请求 `DuplicateKeyException` → 捕获后查已有记录返回（幂等语义），不报错。

```java
public ConsultationVO create(Integer patientId, CreateConsultationRequest req) {
    String sid = StringUtils.hasText(req.getSessionId())
            ? req.getSessionId()
            : UUID.randomUUID().toString().replace("-", "");

    // 幂等：先查一次，避免常规情况下的异常开销
    var exist = consultationMapper.selectOne(
        new LambdaQueryWrapper<Consultation>().eq(Consultation::getSessionId, sid));
    if (exist != null) return toVO(exist);

    try {
        var c = new Consultation();
        c.setPatientId(patientId);
        c.setSessionId(sid);
        c.setChiefComplaint(req.getChiefComplaint());
        c.setStatus(ConsultationStatus.IN_PROGRESS);
        c.setSeverity(Severity.LOW);
        c.setSummaryStatus(SummaryStatus.NONE);
        c.setLastActiveAt(LocalDateTime.now());
        c.setVersion(0);
        consultationMapper.insert(c);
        return toVO(c);
    } catch (DuplicateKeyException e) {
        // 并发穿透：另一个请求已插入，重查返回
        var c = consultationMapper.selectOne(
            new LambdaQueryWrapper<Consultation>().eq(Consultation::getSessionId, sid));
        if (c == null) throw new BusinessException("创建问诊失败，请重试");
        return toVO(c);
    }
}
```

**为什么先查再插 + 捕 DuplicateKey 两层**：先查是常规路径（无异常开销），捕异常是并发兜底（两个请求同时通过第一层检查）。只有一层都不够。

#### 8.2.1 RAG 检索是必经环节

**每一轮用户消息都会调 `retrieve(msg)`，不是可选项。** 这是本项目的核心能力，问诊改造完全保留它。

**检索链路**（`KnowledgeRetrievalService.retrieve`，200 行，现有实现不改）：

| 环节 | 实现 | 说明 |
|---|---|---|
| 分词 | 2–4 字滑窗 + 24 个停用词 + 纯数字过滤 | 中文无空格，用 n-gram 滑窗代替分词器 |
| 召回 | 每个 token 调 `searchByKeywords(keywords, 50)` | 疾病、药品各取 50 条候选，留重排空间 |
| 打分 | `scoreAgainst(name, body, kw)` | `weight = min(kw.length-1, 3)`；命中名称 ×3，命中正文 ×1 |
| 截断 | `Scored<T>` 排序 → `filter(score>0)` → `limit(3)` | 疾病、药品各取 Top3 |

**检索结果包含关联药品**：`formatIllness` 会带出该疾病的关联药品（走 `illness_medicine_rel` 关联表），模型拿到的是「疾病 + 对症药」的完整知识组，不是孤立一条。

**返回格式**（Markdown，直接塞进 prompt）：

```
【参考知识库 · 疾病】
## 疾病：病毒性感冒
- 病因：...
- 症状：...
- 特殊症状：...
- 关联药品：...

【参考知识库 · 药品】
## 药品：布洛芬
- 品牌：...
- 功效：...
- 用法用量：...
- 禁忌：...
```

**返回空字符串表示未检索到**，此时不走「无知识」分支，而是走下面的回落逻辑。

#### 8.2.2 知识上下文回落（Redis）

现有 `DashScopeClient.chatWithHistory` 里有一段回落逻辑，**设计文档此前遗漏，本版补入**：

```java
// DashScopeClient.java:64-74（现有实现）
if (StringUtils.hasText(knowledge)) {
    context = knowledge;
    redisTemplate.opsForValue().set("rag:ctx:" + sessionId, knowledge, 7天);
} else {
    // 本轮没检索到 → 回落到上次的上下文
    var cached = redisTemplate.opsForValue().get("rag:ctx:" + sessionId);
    context = cached != null ? cached.toString() : "";
}
```

**设计意图**：「我咳嗽发烧」→ 检索到病毒性感冒；下一轮「那要吃点什么」→ 分词后全是停用词，`retrieve` 返回空 → 回落上一轮上下文，模型仍然知道在谈咳嗽。

**为什么需要它**：中文追问常省略主语。没有回落，第二轮就会「失忆」，退化成无知识的通用对话。

**常量定义**（`DashScopeClient.java:46-47`）：

```java
private static final String CTX_KEY_PREFIX = "rag:ctx:";
private static final Duration CTX_TTL = Duration.ofDays(7);
```

#### 8.2.3 缓存生命周期必须跟着问诊单走（改造点）

现有 7 天 TTL 是为「单会话无状态聊天」设计的。**搬到问诊后必须收窄**，否则违反 9.4 的「不得存储超出必要范围的健康信息」。

| 场景 | 处理 | 落点 |
|---|---|---|
| 同一张单内的后续消息 | 保留回落 | `chatWithHistory` 原逻辑不变 |
| `complete` 完结 | **删除** `rag:ctx:{sessionId}` | `ConsultationService.complete` |
| `cancel` 取消 | **删除** | `ConsultationService.cancel` |
| 超时关闭 | **删除** | `ConsultationTimeoutJob` |
| TTL 兜底 | 7 天 → **24 小时** | `DashScopeClient.CTX_TTL` |

```java
// DashScopeClient.java —— 新增 public 方法（键前缀是它的私有常量，键的构造与销毁同属一个类）
public void clearContext(String sessionId) {
    if (!StringUtils.hasText(sessionId)) return;
    redisTemplate.delete(CTX_KEY_PREFIX + sessionId);
}
```

**为什么 TTL 也要从 7 天降到 24 小时**：即使有上面的显式清理，也要防「清理失败 / 进程崩溃 / 用户关掉页面就不管了」这些情况。24 小时足够覆盖一次问诊的正常跨度（超时阈值 30 分钟），又不会让健康信息长期挂在 Redis 里。

**为什么不干脆去掉回落**：去掉回落会让多轮追问集体失忆，体验断崖。**收窄生命周期**和**保留回落**不冲突，两个都要做。

**Redis 键的隐私边界**：`rag:ctx:{sessionId}` 的值是疾病/药品知识的 Markdown，**不含用户原话**。用户对话正文在 MySQL 的 `ai_chat_record` 里，删问诊单时一并清理。

**已知设计债（本阶段不修，记录在案）**：当前 `chatStream` 是**假流式** —— 先 `chatWithHistory` 拿全文，再 `for (i += 3) { sleep(20) }` 打出去。真流式需要 DashScope SDK 的 `streamCall`，改动面涉及 `DashScopeClient` 整体重写。**阶段三再做**，因为假流式不影响功能正确性，只影响首字延迟。

**状态校验放在 Controller 还是 Service**：放在 Controller 的 `@PreAuthorize` 里判归属（不查业务数据），在 Service 入口判 `status == IN_PROGRESS`（要查业务数据）。两者职责不同，不能合并。

### 8.4 完结与小结生成

```
患者       Controller    ConsultationService   SummaryService    summaryExecutor   DashScopeClient

```

**为什么完结立即返回而不是等小结**：小结要调 AI，可能 10–30 秒。让用户点完结后干等半分钟是不可接受的。立即返回 `summaryStatus=1`，前端显示「正在生成小结…」，轮询详情接口（或前端 2 秒一次）拿到结果。

**为什么小结失败不阻断完结**：`status=1` 已经落库，`summary_status=3` 只表示小结没生成。用户可以点「重新生成」，也可以就此关闭。**状态机不允许因为外部依赖失败而回退主状态**。

```java
@Transactional
public void complete(Integer id, Integer patientId) {
    var c = consultationMapper.selectById(id);
    if (c == null) throw BusinessException.notFound("问诊不存在");
    if (!patientId.equals(c.getPatientId())) throw BusinessException.forbidden("无权操作");
    ConsultationStateMachine.checkTransition(c.getStatus(), ConsultationStatus.COMPLETED);

    int affected = consultationMapper.update(null,
        new LambdaUpdateWrapper<Consultation>()
            .eq(Consultation::getId, id)
            .eq(Consultation::getStatus, ConsultationStatus.IN_PROGRESS)
            .eq(Consultation::getVersion, c.getVersion())
            .set(Consultation::getStatus, ConsultationStatus.COMPLETED)
            .set(Consultation::getClosedAt, LocalDateTime.now())
            .set(Consultation::getSummaryStatus, SummaryStatus.GENERATING)
            .set(Consultation::getVersion, c.getVersion() + 1));

    if (affected == 0) {
        throw new IllegalStateTransitionException("问诊已被完结或关闭，请刷新后重试");
    }

    // 清缓存 + 提交异步任务都必须等事务提交，否则回滚时缓存已经清掉、状态却没改
    String sid = c.getSessionId();
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            dashScopeClient.clearContext(sid); // 见 8.2.3
            summaryService.generateAsync(id);  // 小结要读整段对话，此时已提交
        }
    });
}
```

**注意 `@Transactional` 与副作用（清缓存 / 提交异步任务）的边界**：两件事都不能直接在事务方法体内做。

| 副作用 | 直接做的后果 |
|---|---|
| `summaryService.generateAsync(id)` | 异步线程可能读到 `summary_status` 还是 `NONE` 的旧快照（事务未提交） |
| `dashScopeClient.clearContext(sid)` | 事务若回滚，缓存已清掉但问诊单还是「进行中」，用户继续对话就失去了知识回落 |

统一用 `TransactionSynchronizationManager.registerSynchronization(...).afterCommit(...)` 包起来。备选方案是把这两个副作用提到 Controller 层，但那样业务逻辑就外泄了 —— 状态流转和它的后果应该内聚在同一个 Service 方法里。

**`cancel` 和 `ConsultationTimeoutJob` 同理**：都是「状态更新 + 清缓存」两步，缓存清理一律放 `afterCommit`。超时任务是逐条独立事务，失败一条不影响其他条。

**为什么不加分布式锁**：为单实例项目引入 Redis 锁是过度设计。要在文档里明确写「多实例部署时必须加锁」，而不是假装问题不存在。

### 9.2 三层鉴权模型

| 层 | 手段 | 落点 |
|---|---|---|
| 认证（你是谁） | JWT Bearer Token | `JwtAuthenticationFilter` |
| 粗粒度授权（你是什么角色） | `@PreAuthorize("hasRole('X')")` | Controller 方法 |
| 细粒度授权（这个数据是不是你的） | `@PreAuthorize("@consultGuard.isOwner(#id, authentication)")` | Controller 方法 |

**为什么细粒度必须查库**：`isAuthenticated()` 只能证明「你登录了」，不能证明「这张单是你的」。越权读别人的问诊记录是医疗数据泄露，必须查库判归属。

`ConsultationGuard`（纯 AI 方案下只有一个方法）：

```java
@Component("consultGuard")
public class ConsultationGuard {

    private final ConsultationMapper consultationMapper;

    /** 患者本人或管理员 */
    public boolean isOwner(Integer id, Authentication auth) {
        if (auth == null) return false;                        // 未登录直接拒
        if (hasRole(auth, "ROLE_ADMIN")) return true;           // 管理员放行（查全量问诊单）
        Integer userId = currentUserId(auth);
        if (userId == null) return false;
        var c = consultationMapper.selectById(id);
        return c != null && userId.equals(c.getPatientId());
    }

    private boolean hasRole(Authentication auth, String role) {
        return auth.getAuthorities().stream()
                .anyMatch(a -> role.equals(a.getAuthority()));
    }

    private Integer currentUserId(Authentication auth) {
        // JwtAuthenticationFilter 已在 request.setAttribute("userId", ...) 写入
        // 这里从 SecurityContext 的 details 取（filter 中 auth.setDetails(userId)）
        return auth.getDetails() instanceof Long l ? l.intValue() : null;
    }
}
```

> **注意 `currentUserId` 的取法**：`JwtAuthenticationFilter.java:67` 做的是 `auth.setDetails(userId)`（`Long` 类型），不是 `request.setAttribute`。所以从 `auth.getDetails()` 取，且必须判 `instanceof Long` 再转 `int`。`AiDoctorController` 现有代码就是这么写的，可以照抄。

**性能提示**：`isOwner` 每次鉴权查一次 `consultation`，Controller 业务方法可能再查一次，同一请求查 2 次。id 是主键查询，成本可接受。**本阶段不优化**，若后续要优化用 request attribute 缓存（不是 `@Cacheable`，避免缓存污染越权判定）。

## 十、数据一致性与事务边界

### 10.1 现状：零事务

`grep -rl "@Transactional" backend/src/main/java` → **0 个文件**。

这意味着以下操作目前**没有任何原子性保证**：

| 操作 | 涉及写 | 失败后果 |
|---|---|---|
| 注册 | `sys_user` INSERT | 单写，暂无问题 |
| 问诊完结（新） | `consultation` UPDATE + `ai_chat_record` INSERT（系统消息） | 状态改了但消息没写，用户看不到结论 |
| 问诊删除（新） | `consultation` 逻辑删 + `ai_chat_record` 软删 | 单删了消息还在，历史里能查到孤立记录 |

### 10.2 事务边界设计

**原则：事务边界在 Service 方法上，不在 Controller、不在 Mapper。**

| Service 方法 | 事务 | 边界理由 |
|---|---|---|
| `ConsultationService.create` | `@Transactional` | 建单 + 写首条系统消息，两写需原子 |
| `ConsultationService.complete` | `@Transactional` | 改状态 + 改 `summary_status`，两写需原子 |
| `ConsultationService.cancel` | `@Transactional` | 改状态 + 写审计 |
| `ConsultationService.delete` | `@Transactional` | 逻辑删单 + 软删消息，两写需原子 |
| `ConsultationSummaryService.generate` | **不加**，但内部两次 UPDATE 要各自独立提交 | 调 AI 耗时 10–30 秒，**绝不能包在事务里**（会长时间占用连接） |
| `ConsultationMessageService.append` | **不加** | 纯单表 INSERT，加事务只是开销 |
| `ConsultationTimeoutJob` | **逐条调 Service 方法**，不整体事务 | 500 条里 1 条失败不该回滚 499 条 |

**为什么小结生成绝对不能加 `@Transactional`**：Druid 连接池 `max-active: 20`。如果小结生成包在事务里，每次调用 AI 都会占住一个连接 10–30 秒，20 个并发就把连接池耗光，整个应用挂死。这是最容易犯的致命错误。

正确做法：调 AI 在事务外，拿到结果后用一个短事务写库。

```java
// 错误示范 —— 不要这么写
@Transactional
public void generate(Integer id) {
    var summary = dashScopeClient.chatWithSummary(...);  // ← 10-30 秒，全程占连接
    consultationMapper.updateById(...);
}

// 正确做法
public void generate(Integer id) {
    var summary = dashScopeClient.chatWithSummary(...);  // ← 事务外
    summaryWriter.write(id, summary);                    // ← 短事务，只包 UPDATE
}
```

**为什么 Job 不加整体事务**：定时任务批量处理时，整体事务会导致一条死锁就把整批卡住，且长时间持有锁。正确做法是每条独立事务（调 `@Transactional` 的 Service 方法），失败记录日志继续。

### 10.3 幂等设计

| 场景 | 幂等手段 | 冲突处理 |
|---|---|---|
| 重复创建问诊 | `uk_session` 唯一索引 | 捕 `DuplicateKeyException` → 查已有记录返回 |
| 重复完结 | `WHERE status = 0` 条件更新 | 影响行数 0 → 抛 `IllegalStateTransitionException`（409） |
| 重复取消 | `WHERE status = 0` 条件更新 | 影响行数 0 → 静默返回成功（取消是幂等操作） |
| 重复生成小结 | `WHERE summary_status IN (0, 3)` 条件更新 | 影响行数 0 → 说明已在生成中，直接返回 |
| 重复超时关闭 | `WHERE status = 0` 条件更新 | 影响行数 0 → 静默跳过 |
| 重复删除 | 逻辑删除 + `WHERE deleted = 0` | 影响行数 0 → 静默返回成功 |
| 重复发消息 | **不做幂等** | 消息重复可接受，前端有 `typing` 状态拦截 |
| 重复清理 RAG 上下文 | `RedisTemplate.delete(key)` 本身幂等 | key 不存在时返回 false，不抛异常，直接忽略 |

**为什么「重复取消」和「重复完结」处理不同**：取消是「让它别继续」，重复调用的期望结果一致，静默成功更友好。完结是「产出结论」，重复调用说明用户可能在多标签页操作，返回 409 让他刷新能看到真实状态。**语义不同，处理就该不同**，不能一刀切。

**为什么消息不做幂等**：代价大（要给每条消息生成 `client_msg_id` 并建唯一索引），收益小（重复消息不影响数据正确性）。这是有意识的取舍，不是遗漏。

**RAG 上下文清理的幂等性**：`complete` / `cancel` / 超时关闭三条路径都会调 `dashScopeClient.clearContext(sessionId)`（见 8.2.3）。同一张单被重复清理、或清理时 key 已过期，`RedisTemplate.delete` 都只是返回 `false`，不会抛异常。**不需要额外的幂等保护**，但清理动作必须放在状态更新成功之后，避免「状态没改成功却先把缓存清了」。

### 10.4 并发场景清单（纯 AI 方案）

| 场景 | 风险 | 防护 |
|---|---|---|
| 患者点完结 + 定时任务判超时 | 终态被覆盖（「已完成」被改成「超时关闭」） | `WHERE status = 0` 条件更新，只有一个成功 |
| 双击完结 / 多标签页操作 | 第二次请求报错或写两遍 | 同上，第二次影响行数 0 → 409 |
| 同一患者并发创建问诊 | 建出两张单 | `uk_session` 唯一索引 |
| 用户连点「重新生成小结」 | 两个异步任务同时跑，后完成覆盖先完成 | `WHERE summary_status IN (0,3)` 条件更新，只有一个能进 `GENERATING` |
| 同一 session 并发发消息 | `last_active_at` 后写覆盖前写 | 无需防护（时间戳覆盖无实质影响） |
| 并发写 `ai_chat_record` | 无冲突 | 自增主键，无唯一约束 |

> 纯 AI 方案少了「两医生抢单」，但前四条仍是真实的并发场景，且第一条（完结 vs 超时）在生产里确实会发生。这就是 3.5 节说的补偿。

### 10.5 需要加的 MyBatis-Plus 插件

**现状**（`backend/src/main/java/com/mediquery/config/MyBatisPlusConfig.java`）：只注册了 `PaginationInnerInterceptor`。

**需要加三个**：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    var interceptor = new MybatisPlusInterceptor();
    // 1. 分页 + 上限保护（现有项目无 size 上限，可被刷爆）
    var pagination = new PaginationInnerInterceptor(DbType.MYSQL);
    pagination.setMaxLimit(100L);
    interceptor.addInnerInterceptor(pagination);
    // 2. 乐观锁：@Version 生效的前提
    interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
    // 3. 防全表更新/删除：没有 WHERE 的 UPDATE/DELETE 直接抛异常
    interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());
    return interceptor;
}
```

**`OptimisticLockerInnerInterceptor` 是 `@Version` 生效的必要条件** —— 不加它，实体上标 `@Version` 也无效。这是个常见坑，值得在文档里单独标注。

**`setMaxLimit(100L)` 补的是现有漏洞**：全项目 grep `setMaxLimit` 0 命中，前端传 `size=999999` 就能让后端拉全表。这是把既有缺口和新改造一起修。

**`BlockAttackInnerInterceptor` 的风险**：会拦截没有 WHERE 的批量更新。若现有代码有全表更新会直接报错。实测现有代码无此类操作（`updateById` / `LambdaUpdateWrapper` 都带条件），可安全加。**但要在阶段一加完后跑一遍全接口回归**。

### 11.3 nginx SSE 配置（必须改，否则 Docker 下流式失效）

**现状**（`frontend/nginx.conf`，22 行）：只有

```nginx
location /api/ {
    proxy_pass http://backend:8080/api/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

**问题**：nginx 默认 `proxy_buffering on`，会把后端逐条 flush 的 SSE 事件攒在缓冲区里，客户端要等缓冲满或连接关闭才收到 —— 流式退化成一次性返回。本地 `vite dev` 走的是 vite proxy（已加 `res.flushHeaders()`），所以开发环境完全看不出这个问题。

**必须加**：

```nginx
location /api/v1/consultations/ {
    proxy_pass http://backend:8080/api/v1/consultations/;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;

    # SSE 关键三行
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;   # 必须 > 后端 SseEmitter 的 120s

    gzip off;                  # gzip 会攒包，必须关
}
```

**超时对齐**：后端 `SseEmitter(120000L)` = 120s，nginx `proxy_read_timeout` 必须**大于**它（设 300s），否则 nginx 先断连，客户端收到的是「连接中断」而不是后端的 error 事件。

## 16. 数据库迁移交给 Flyway（2026-11-07）

### 16.1 为什么要改

这一轮加问诊信息卡时真踩过一次：代码里 `Consultation` 多了 4 个字段，`init.sql` 也同步改好了，但**跑在 3306 上那个库不知道**。后端启动不报错，一开单就 `Unknown column 'duration_desc' in 'field list'` 500 —— 因为 `init.sql` 只在 Docker 卷为空时被 `docker-entrypoint-initdb.d` 执行一次，对已存在的库完全不起作用。当时的修法是手写一段 `ALTER TABLE` 敲进去。

这个坑不是「这次手滑」，是结构性的：**建表脚本和数据分离、只在特定时机跑一次、改了就没人知道库里到底是什么版本**。换台机器部署、换个同事接手，同一个坑会重新踩一遍。

### 16.2 结构

```
backend/src/main/resources/db/
├── migration/
│   ├── V1__baseline.sql           # 181 行，8 张表的基线（从 init.sql 拆出，去掉 DROP TABLE）
│   ├── V2__intake_slots.sql       # 16 行，一条 ALTER 加信息卡 4 列
│   └── V3__drop_legacy_tables.sql # 9 行，DROP 掉 feedback / sys_doctor 两张遗留空壳
└── seed.sql                       # 69 行，种子数据（手动执行，不是迁移）
```

**为什么 V1 里没有 `DROP TABLE` 和 `CREATE DATABASE`**：`init.sql` 是「可重复执行」的一次性脚本，所以每张表前都有 `DROP TABLE IF EXISTS`；迁移脚本不是——它只应该在一张空库上从零建起，`DROP` 会让"重跑迁移"变成"删库"。`CREATE DATABASE` 也不该由应用代劳，库的存在是部署前置条件。

**为什么种子数据独立**：种子不是结构。结构脚本必须能在任何环境跑出同样结果，种子脚本写的却是「10 条示例疾病」这种业务数据。混在一起会让「改一条示例数据」也算一次迁移。

**为什么还有个 V3 删表**：`feedback` 和 `sys_doctor` 在项目收敛成纯在线问诊时就删了模块和实体，但当时只改了 `init.sql` —— 已经建好的库没人动它，于是这两张表一直躺在生产库里（`feedback` 0 行、`sys_doctor` 8 行种子医生，没有任何读取方）。留着的代价是持续误导：有 `sys_doctor` 表就有人以为该有医生功能。`V3` 用 `DROP TABLE IF EXISTS` 清掉，`IF EXISTS` 是为了让新库（V1 就没建这两张）也能顺利跑过。

**为什么 V2 是 `ALTER` 而不是去改 V1**：V1 一旦发布（哪怕只在本机跑过一次），改它就等于让"跑过 V1 的库"和"没跑过的库"走向两条不同的历史。`validate-on-migrate: true` 会直接用 checksum 不匹配拒绝启动。这条规则很硬，但正是它让迁移可信。

### 16.3 配置

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: ${FLYWAY_BASELINE_VERSION:1}
    validate-on-migrate: true
    table: flyway_schema_history
```

- `baseline-on-migrate` 是给**已经存在的库**准备的。那些库是 `init.sql` 时代建的，`flyway_schema_history` 不存在，Flyway 默认会拒绝在非空库上运行；这个开关让它记一条基线后继续。
- `baseline-version` 默认 1。**老库（结构已等于 V2）要设成 2**，否则 Flyway 从 V1 开始重放、撞上"表已存在"。
- `validate-on-migrate` 保持 `true`。它会在启动时校验已执行过的迁移文件有没有被改动过 —— 这是「迁移历史可信」的唯一保障，别为了图省事关掉。

### 16.4 测试为什么不用 Flyway

`application-test.yml` 里明确写了 `spring.flyway.enabled: false`，测试继续走 `src/test/resources/schema-h2.sql`（H2 内存库）。

**不是偷懒，是 H2 跑不了**：迁移脚本里有 `ENGINE=InnoDB`、`WITH PARSER ngram`、表级 `COMMENT`，H2 的 MySQL 兼容模式不认这些。硬让它跑，要么改迁移脚本迁就 H2（那就等于生产环境在将就测试环境），要么在迁移脚本里写 H2 分支（那就不叫迁移脚本了）。

代价是**迁移脚本本身没有自动化兜底**。兜底分两层：

1. `SchemaDriftTest` 把 `db/migration/*.sql` 拼起来（含 `ALTER` 解析）、和 `schema-h2.sql` 比对表名与字段名集合。它能抓到「加了列忘了同步 H2」，抓不到「SQL 语法在 MySQL 上是错的」。
2. 「在空库上真跑一次 Flyway」只能人手做。**这一轮做过，记录在 16.5。**

- **回滚没有自动化**。Flyway 社区版不支持 `undo` 迁移，要回退只能写一个新的正向迁移改回去。

### 16.8 部署时容易忽略的几点

- `seed.sql` 不会自动执行。`docker-compose` 的 `init.sql` 挂载已经移除——入口脚本只在卷为空时跑一次，而 Flyway 要等后端启动才跑，时序对不上（挂 `seed.sql` 进去会在表还不存在时 `INSERT` 失败）。要种子就等后端起来后手动执行。
- **`FLYWAY_BASELINE_VERSION` 是"每台机器各自的事"**，所以它在 `.env` 里（gitignore 掉的），不在 `application.yml` 的默认值里。`application.yml` 的默认值保持 1（新库语义），老库靠 `.env` 覆盖到 2。
- 回滚没有自动化。Flyway 社区版不支持 `undo`，要回退就写一个新的正向迁移改回去——这是它比 `undo` 安全的地方（历史永远单向累积）。真到了必须还原数据的地步，用上面那份 `mysqldump`。

## 17. 死代码审计与断链修复（2026-11-09）

收尾阶段做了一遍「到底还有没有没人用的东西」的审计。三层结论分得很开：**页面层零死代码、类层零死代码、pom 零冗余依赖，但 Service 层藏着一批空壳，而且审出一个真 bug。**

### 17.1 三个层次的审计口径

| 层 | 方法 | 结论 |
|---|---|---|
| 前端页面 | 路由表 vs `src/**/*.vue` 逐个比对 | 9 个 .vue（6 页面 + 2 布局 + App）全部被引用，**零死页面** |
| 后端类 | 类名在整个 `src` 中的出现次数 | 73 个 .java 里只有 `OpenApiConfig` 只出现 1 次，但它是 `@Configuration` 靠扫描注册，**正常** |
| pom 依赖 | 14 项依赖逐个查使用痕迹 | **全部有痕迹**，无一冗余 |

顺带记一个踩过的坑：第一版前端审计脚本报「6 个页面未被路由引用」，是**假警报**——脚本拿 Windows 反斜杠路径（`pages\public\HomePage.vue`）去比对路由里的正斜杠 `@/pages/public/HomePage.vue`，字符串永远不等。这类脚本自己出错时的表现和"真的发现死代码"一模一样，必须抽查一条再信。

### 17.2 真 bug：RAG 的「疾病→关联药品」从来没输出过

这是本轮最值得记的发现。

`KnowledgeRetrievalService.formatIllness` 里一直有这段：

```java
var medicines = i.getMedicines();
if (medicines != null && !medicines.isEmpty()) {
    ... sb.append("- 关联药品：").append(names);
}
```

但 `Illness.medicines` 是 `@TableField(exist = false)` 的关联字段，全仓只有 `IllnessService.getById` 会填它——而 `getById` 服务的「疾病详情页」在重构时已经被删了，**它的调用方是 0**。

所以生产路径上 `medicines` 永远是 `null`，那一行从来没输出过。**模型一直拿到半条知识**：知道「病毒性感冒」是什么，不知道通常配哪些药。

为什么 284 个测试全绿？因为 `KnowledgeRetrievalServiceTest` 用的是 mock 的 `RetrievalStrategy`，直接塞 `Illness` 对象进去，`medicines` 自然是 `null`——测试断言的是「命中哪几个病」，没人断言「关联药品那行在不在」。**断言的范围决定了测试能挡住什么。**

修法：`KnowledgeRetrievalService` 自己注入 `IllnessMedicineRelMapper`，在 `rankIllnesses` 选出 Top-K 之后逐个补：

```java
for (var illness : ranked) {
    attachMedicines(illness);
}
return ranked;
```

三个刻意的取舍：

- **只给最终入选的 3 条补，不给 50 条召回窗口补**——后者是 50 次多余 SQL，为了 47 条马上被丢掉的候选付出代价。
- **查失败只 warn 不抛**——关联表挂了不该让整轮问诊跟着挂，少一行知识比问不出话好。
- **`getMedicines() != null` 就跳过**——允许上游（测试、将来的批量查询）自己填好，不覆盖。

新增两条用例钉住：`medicinesAreAttachedBeforeFormatting`（mock 返回阿莫西林 → 断言 context 含「关联药品」和「阿莫西林」+ verify 调过 mapper）、`relLookupFailureIsSwallowed`（mapper 抛异常 → 断言 context 仍含病名、不含「关联药品」）。

**同一处还捞到一个白查**：`Illness.categoryName` 全仓只有定义、**没有任何代码读过**，`fillCategoryNames` 每次召回都白查一次 `illness_category`。既然已经在补关联数据，顺手把它也喂给模型：`formatIllness` 新增 `- 常见科室：{categoryName}` 一行。查都查了，不用就是浪费。

### 17.3 零调用 CRUD：为已删除的页面留的空壳

| Service | 方法 | main 调用方 | test 调用方 |

| `IllnessService` | `search` | 0 | 7 |

### 17.4 顺带清掉的缓存层

`@Cacheable` / `@CacheEvict` 全仓只出现在上面那些方法上（`medicine` / `illness` 两个 cache）。方法都零调用了，**这两个缓存从上线起就从来没被写过**——留着是一层看着很完整的假象。

### 17.5 三个「前端没调用」的端点，三种处置

审计发现后端 25 个端点里有 3 个前端从不调用。**但它们不是同一类东西**，处置也就不一样：

| 端点 | 判定 | 理由 |
|---|---|---|
| `GET /api/v1/stats` | **保留 + 接线** | `CorsPreflightIntegrationTest` 拿它当 CORS 探测靶子（4 处），删了会打断测试；而且它是有意义的公开数据 |

`GET /{id}/intake` 的删除有个细节值得记：删掉之后同路径还剩 `PUT /{id}/intake`，所以实测返回的是 **405 而不是 404**——路由还在，只是不支持 GET。两者都能证明端点没了，但报告里得说清是哪一个。

**`/stats` 接线**：`HomePage.vue` 原本完全没接它，而设计文档第 2217 行早就写着「落地页，接 /stats 真实计数」——**文档承诺了、代码没做，这一条一直在文档里躺着**。现在补上：首屏底部两行真实计数（已完成 N 次问诊 / 知识库收录 N 种疾病 · N 种药品）。拿不到就整条不渲染，**不摆一个编出来的数字**——退回 `0 次问诊` 看着更像真的，反而更误导。

## 18. 知识库改造成症状图谱（2026-11-09）

### 18.1 为什么原来的东西不叫知识库

改造前的「知识库」是 `illness` / `medicine` / `illness_medicine_rel` 三张业务表加一条 ngram 全文索引。实测主诉召回：

| 主诉关键词 | 命中疾病数 |
|---|---|
| 失眠 | 0 |
| 腰痛 | 0 |
| 头晕 | 0 |
| 腹泻 | 0 |
| 心悸 | 0 |
| 咳嗽 | 2 |
| 发热 | 3 |

问题**不是数据少**，是结构错了：

- `illness.symptom` 是 `VARCHAR` 顿号串（「鼻塞、流涕、打喷嚏…」），只能 `LIKE` 或全文匹配。患者说「拉不出来，蹲半天」，分词器切不出「排便费力」，就永远命不中。
- `illness_medicine_rel` 只有两个 ID，缺适应症、缺一线/二线、缺证据等级。结果是**阿莫西林（抗生素）挂在病毒性感冒（病毒感染）上**，模型照着念就是在给错误的用药暗示。
- 科室信息只在 `illness.category_id` 里一对一存着，没法表达「同一个病，先挂 A 科再转 B 科」。

### 18.2 对标了什么

| 项目 | 规模 | 关键做法 |
|---|---|---|
| CMeKG | 6310 疾病 / 19853 药物 / 100 万+ 三元组 | 12 类实体 + 12 类关系；症状是独立实体；描述用六元组 `{e1, e1_pro, rel, rel_pro, e2, e2_pro}` |
| LingShu | 1733 万实体 / 3947 万关系 | 16 类实体；64 种三元组 + 35 种四元组；**四元组用来给关系加条件**（同药在不同病下效果不同） |
| PrimeKG | 17080 疾病 / 405 万边 / 20 数据源 | **一张边表**容纳 29 种关系（`relation, display_relation, x_id, x_type, x_name, x_source, y_*`） |
| 讯飞晓曼导诊 | 169 科室 / 13000+ 症状 / 5200+ 疾病 | 症状→科室属医疗决策逻辑，走规则引擎 / CDSS，不走 RAG；验收标准是「首选科室与人工分诊一致率 ≥90%、红旗召回 100%」 |

提炼出四条落到本项目的规律：

1. **边表优于给每类关系单开一张表**——本项目的修正结果是：新关系新表，但同类关系（疾病→用药）只在原表上加列，不另建一张语义重复的表。
2. **关系必须带条件**——`illness_medicine_rel` 加 `indication` / `line_of_treatment` / `evidence_level`。
3. **症状必须是独立实体**——`symptom` + `symptom_alias`，口语先归一再检索。
4. **图谱的价值在多跳**——症状 → 疾病 → 科室，两跳；只做一跳等于换了个 LIKE。

### 18.3 数据模型（Flyway V4）

迁移脚本 `backend/src/main/resources/db/migration/V4__symptom_graph.sql`：

| 表 | 作用 | 关键列 |
|---|---|---|
| `symptom` | 症状主表 | `name`（UNIQUE）、`body_part`、`category`、`description`、`status` |
| `symptom_alias` | 同义词 | `symptom_id`、`alias`（UNIQUE）、`weight` |
| `disease_symptom` | 疾病-症状边 | `illness_id`、`symptom_id`、`weight`、`is_cardinal`、`is_red_flag` |
| `disease_department` | 疾病-科室边 | `illness_id`、`department`、`priority`、`reason` |
| `illness_medicine_rel`（ALTER） | 疾病-用药边 | 新增 `indication`、`line_of_treatment`、`evidence_level` |

`weight` 是 `DECIMAL(3,2)`（0.00–9.99），因为要表达「核心症状 0.90、伴随症状 0.50」这种强弱，整数表达不了。`is_cardinal` 与 `weight` 是两个维度：前者是「有没有它很关键」（用于同分时的排序），后者是「命中它加几分」。

`disease_department.priority` 用 `INT` 而不是 varchar 排序，因为「首选/次选」是次序不是标签，排序必须稳定。

### 18.4 检索链路（两跳）

```
用户主诉文本
   ↓ SymptomNormalizer.normalize()
   ├─ 加载词表（symptom.name + 全部 alias，UNION ALL 拍平）
   ├─ 按 matchText 长度降序排（最长匹配优先，避免「喉咙」抢走「喉咙痛」）
   ├─ boolean[] 区间占位，已匹配的字符不再参与更短的匹配
   └─ NegationMatcher.isNegated() 过滤（「没有发烧」不算发烧）
   ↓ List<NormalizedSymptom>
DiseaseSymptomMapper.selectIllnessesBySymptoms()
   ├─ SUM(ds.weight) AS score       ← 命中越多、越核心，分越高
   ├─ MAX(ds.is_red_flag)           ← 红旗向上冒泡
   └─ SUM(is_cardinal)              ← 同分时核心症状多的排前面
   ↓ Top 3 疾病
DiseaseDepartmentMapper / DiseaseMedicineMapper
   └─ 科室按 priority、用药按 line_of_treatment（0=未分级折成 9，永远排最后）
```

`SymptomNormalizer` 的词表**整表捞进内存**而不是拿输入去数据库筛：词表几百行，整表捞才不会「切错一个词就永远命不中」；带 5 分钟 TTL，加载失败沿用旧缓存只 `warn`。

`GraphRetrievalService.retrieve()` 任何一层失败都返回 `Result.empty()` 不抛异常，`KnowledgeRetrievalService` 收到空结果才退回原来的关键词路径——图谱是新链路，不能成为新的单点故障。

### 18.5 提示词里长什么样

`formatGraph()` 产出四段：

```
【本轮识别到的症状】
- 排便费力（你说的是「拉不出来」）· 部位：腹部

【参考知识库 · 可能相关的疾病】
## 疾病：便秘
- 病因：…
- 典型表现：…
- 建议科室：内科（…）

【需要立即就医的提示】
- 胃溃疡（黑便、呕血）
```

三个刻意的设计：

- **回显患者原话**（`你说的是「拉不出来」`）——让患者知道系统是真的听懂了，而不是套模板。
- **红旗疾病单列在最后一段**，不混进「可能相关的疾病」里。混在一起时模型会把「可能是胃癌」当普通候选念出来，患者听到的是惊吓不是提醒。
- **没有 `indication` 的药一律不输出**。知识库里没有针对本病的明确用药建议时，输出的是「不要自行服药」，而不是把关联表里的药名倒出来。

## 19. 检索质量：先立尺子，再改算法（2026-11-10）

第 18 章把「一条 LIKE」换成了症状图谱两跳，链路通了，但**没有任何数字能说明它到底有多准**。这一章记的是补上这个缺口的过程，以及过程中发现的两个真问题。

### 19.1 为什么顺序是「评测集 → IDF → 追问 → 症状组合」

四件事都能提升「智能」，但它们的价值不可比：

| 步骤 | 做什么 | 解决什么 | 为什么排这个位置 |
|---|---|---|---|
| 1 | 评测集 + 基线 | 没有它，后面每一步都是拍脑袋 | 必须最先 |
| 2 | 打分加 IDF | 「发热」这种人人都有症状降权，「骨擦音」这种罕见症状升权 | 半天，改动最小 |
| 3 | 主动追问 | 让图谱从「查」变成「问」 | 三天内收益最高 |
| 4 | 症状组合 + 排除症状 | 咽痛**或**吞咽困难都算；说了「不发烧」就别再推流感 | 最后 |

第 4 件放最后有个具体原因：它降的是「误报」，而误报要能算出来才看得见效果 —— 依赖第 1 步的负例集。

### 19.2 评测集（`backend/src/test/resources/eval/retrieval-cases.json`）

32 条用例，字段 `id / complaint / expectDiseases / expectDepartment / expectRedFlag / note`。三条设计上的取舍：

**① 27 条正例 + 5 条负例。** 负例（c20 失眠、c21 头晕眼前发黑、c22 心慌、c23 腰疼、c24 拉肚子）的 `expectDiseases` 是空数组。它们验的不是「召回率」，而是**「没有就说没有」** —— 知识库里确实没有这几类病，硬凑一个「焦虑症」出来比什么都不返回更糟。

**② 每条 `note` 写清楚「这条验的是什么」。** 用例会越加越多，半年后没人记得 c29 和 c17 有什么区别（其实是：c17 症状明确、c29 只有「嗓子里有脓点」这种半口语说法，验的是别名覆盖）。

**③ 用例本身要被测试。** `datasetReferencesRealEntities` 断言 `expectDiseases` 里每个病名都真实存在于 `illness` 表、每个科室都存在于 `illness_category` 表。理由写在这条测试的注释里：写一个库里没有的病名，Recall 永远算未命中，人看到的是「准确率偏低」，去翻算法 —— 实际是用例写错了。

`RetrievalEvalTest` 的及格线是常量：`MIN_RECALL_AT_3 = 0.55`、`MIN_MRR = 0.45`、`MIN_DEPARTMENT_AGREEMENT = 0.45`。**红旗召回用 `isEqualTo`，不是 `isGreaterThanOrEqualTo`** —— 漏报一条红旗是安全事故，不是指标退步。

**踩到的一个坑：surefire 在 Windows 上会吞掉 System.out。** 日志里只剩一行 `Unable to create temporary file ...stdout-*.deferred`，评测表一个字都看不到。所以报表改为 `Files.writeString(target/retrieval-eval.txt)`，看结果一律读文件而不是读控制台。

### 19.3 IDF 打分

原公式 `score = SUM(ds.weight)`。问题在只有 10 个病时刚好、病一多就必然失效：「发热」能命中 3 条病时它还算是信号，能命中 200 条时它就是噪声。引入 IDF 后：

```
score = SUM(weight × idf)，idf = ln((N + 1) / (df + 1)) + 1，N = 已发布疾病总数
```

用 `+1` 做平滑而不是直接 `ln(N/df)`，是为了让 `df = N` 的症状退化成 1.0 而不是 0 —— 「人人都有」意味着**这条证据没区分度**，不意味着「有这条症状就不可能是这个病」。最后那个 `+1` 保证系数永远 ≥ 1，不会把权重整个抹掉。

**一个必须写下来的实现细节：`SUM(w) × idf ≠ SUM(w × idf)`。** 后来的重构把 SQL 里的 `SUM(weight)` 拆成了「每条边一行」，就是因为压扁成一行之后再也没法按每条边各自的 idf 乘回去。`DiseaseSymptomEdge` 这个 DTO 存在的唯一理由就是这个。

`DiseaseScorerTest` 里最关键的一条是 `rareSymptomOutweighsCommonOne`：不加 idf 时常见病甲排第一，加上之后罕见病乙反超。**它钉的不是「idf 被算出来了」，是「加了 idf 之后排序真的会翻转」。** 只断言数值的测试，把 idf 乘在错的地方也照样绿。

**诚实的结论：评测分数一分没变。** Recall@3 92.6% / MRR 0.889，与加 IDF 之前完全持平。原因是知识库只有 10 个病，df 顶多 3，撑不开 `ln(11/4) = 1.01` 这种系数差。这一步是为规模化打底，不是为当下刷分。

### 19.4 主动追问

图谱能回答「这些症状像什么病」，但患者说的往往不够。追问的价值在于**问什么**：直觉让人问「这个病还有什么症状」，结果问出每个候选病都有的「发热」—— 答什么都收窄不了。

`FollowUpQuestionService` 的打分是：

```
score = split × cardinalFactor × weight
split = 4 × p × (1 - p)，p = 命中该症状的候选数 / 候选总数
```

`split` 是信息增益的形状（p=0.5 时取最大值 1），不用真算熵：全部候选都有 → 0，只有一个候选有 → 接近 0，**一半对一半 → 1**。`cardinalFactor = 0.7 + 0.3 × (核心症状占比)`，让「核心症状」比「边缘症状」优先级略高，但不至于压过区分度本身。

**修掉的一个真问题：两个症状如果命中的候选完全是同一批，它们提供的是同一条信息。** 报表首轮出现过 `↳ 追问：搏动性头痛、单侧头痛` —— 这两个都只有偏头痛有、另外两个候选都没有，答完得到的结论一模一样。问一个是鉴别，问两个是让人重复回答。修法是按 `hitDiseases` 集合去重（`LinkedHashSet<List<String>>`），改完变成 `↳ 追问：搏动性头痛、上腹部疼痛`。

**连带修掉的一个测试问题**：`asksTheSplittingSymptom` 原来断言「必须包含『吞咽困难』」。但「咽痛」「吞咽困难」「鼻塞」「全身酸痛」「恶寒」对那三个候选的分布完全一样（都只有一个候选有），信息量相同，选哪个都在理 —— 这条断言锁定了一个没有意义的实现细节，下次调权重就会红，还红得没有信息量。改成断言**性质**：问出来的每一条都同时有 `hitDiseases` 和 `missDiseases`（真能分开候选），且两条问题的命中集不重复。

### 19.5 提示词里的约束

`SYSTEM_PROMPT` 的「【关于知识库】」段追加：

```
参考条目里可能有一节叫「可以追问的问题」。那不是让你照着念的表单，
是系统算出来「问了最能区分这几种可能」的几个点 —— 这一轮最多挑一个、
最多两个问出来，用你自己的话问，不要写成「有没有 A？有没有 B？」的问卷。
用户已经在前面说过的，不要再问一遍。危险信号出现时先让他就医，不要追问细节。
```

**端到端实测（cid=19，主诉「嗓子疼，发烧两天」）**，首帧 `sources = ["扁桃体炎", "病毒性感冒", "风寒感冒"]`、`suggestDept = ["耳鼻喉科", "呼吸内科"]`，AI 回复：

> 听起来咽痛和发热已经持续两天了，确实挺难受的。为了帮你判断更可能的方向，我问两个关键点：1. 发烧时是不是特别怕冷、穿很多衣服还发抖（医学上叫"恶寒"）？ 2. 咽喉疼的时候，吞口水都困难吗？或者你照镜子看看，扁桃体位置有没有红肿、白点或脓苔？这两个信息能帮我们区分是普通病毒性感冒、风寒感冒，还是细菌性扁桃体炎。

它问的正是系统算出来的「恶寒」和「吞咽困难」，不是模型自由发挥；也没写成问卷，用了医生口吻。

## 20. 排除症状：一个空实现的自我拆穿（2026-11-10）

### 20.1 为什么这件事比"多召回一个病"重要

第 19 章做完后，系统已经会主动追问了。但有个方向是反的：

> 患者说「咳嗽三天，**没有发烧**」，
> 系统照样把「病毒性感冒」排在第一位，理由是「发热」那条边。

漏掉一个病，用户看到的是"系统没提"。**把用户主动排除的方向又捡回来，用户看到的是"它没听我说话"** —— 这在问诊场景里比漏诊更伤信任，因为它颠倒了患者刚说过的事实。

### 20.2 数据链路：否认在归一化这一层就被扔了

`SymptomNormalizer` 原本只返回命中的症状：

```java
if (!overlaps(hit, taken) && !NegationMatcher.isNegated(text, position)) {
    hits.put(symptomId, candidate);   // 被否定的直接不进
}
```

`NegationMatcher` 判断得没错，但**判完就丢**。下游 `GraphRetrievalService` 拿到的只有一个「命中列表」，根本不知道"发烧"这两个字出现过、而且前面是个"没有"。

改造：`SymptomNormalizer` 新增

```java
public record Normalized(List<NormalizedSymptom> hits,
                         List<NormalizedSymptom> denied) {}

public Normalized normalizeWithNegatives(String text) { ... }

public List<NormalizedSymptom> normalize(String text) {   // 老 API 语义不变
    return normalizeWithNegatives(text).hits();
}
```

`sink` 从原来的一路 `hits` 改成按是否被否定分流到两个 map；最后 `denied.keySet().removeIf(hits::containsKey)` ——**同一症状既承认又否认时以承认为准**（"昨天没烧，今天烧了"）。

保留老 `normalize()` 是刻意的：`FollowUpQuestionService` 等 6 处调用方零改动，回归风险压到最小。

### 20.3 第一版：给被否认的边打对折

最直觉的做法是"打折"。`DiseaseScorer` 加个系数：

```java
private static final double DENY_FACTOR = 0.5;   // ← 后来删了
...
if (denied.contains(edge.getSymptomId())) {
    weight *= DENY_FACTOR;
}
```

当时的理由写得很像那么回事：**"没有发烧"的可信度天然低于"我发烧了"**（患者可能记错、可能烧过没说清），所以不该和肯定句同权。

补了 3 条带否定的评测用例（c33/c34/c35）后跑评测：

`Recall@3` 92.6% → **93.3%**，`MRR` 0.889 → **0.900**，科室一致 88.9% → **90.0%**。

看起来成了。**但这个涨幅是假的。**

### 20.4 控制实验：把系数改回 1.0，指标一动不动

加了 3 条用例，本来就会多 3 条"该过的"。要判断新机制有没有用，得做控制实验：**把 `DENY_FACTOR` 从 0.5 临时改回 1.0（等价于彻底关闭否认）**，同一批 35 条用例重跑——

```
EVAL cases=35 有期望=30 无期望=5 | Recall@3=93.3% (28/30) | MRR=0.900 | 科室一致=90.0% (27/30) | 红旗=7/7 | 误报=0/5
```

**一模一样。**

结论：第一版实现**对排序毫无影响，是个空实现**。如果没做这个对照，它会带着"提升 0.7 个百分点"的说法进仓库，然后在真实病例上继续把用户排除的病排第一。

### 20.5 根因：打对折 ≠ 排除

算术很简单。「病毒性感冒」的那条发热边权重 0.6：

| 场景 | 得分 |
|---|---|
| 患者没说发烧 | 0.6 |
| 患者说"没有发烧"，第一版 | 0.6 × 0.5 = **0.3** |
| 患者说"没有发烧"，本该 | **0** |

0.3 分仍然比很多"正常命中"的病高。**打折只是让被否认的证据变弱，没有让它停止说话。** 患者明确排除的东西，凭什么还能贡献三分之一的分？

### 20.6 改成清零，连带核心标记一起清

```java
if (denied.contains(edge.getSymptomId())) {
    weight = 0.0;
}
...
if (Boolean.TRUE.equals(edge.getIsCardinal()) && weight > 0.0) {
    acc[1]++;          // cardinalHits 也是排序依据，不能让它带分
}
```

第二处容易漏：`cardinalHits` 是并列时的第二排序键。如果被否认的核心症状仍计入 `cardinalHits`，两个病同分时它反而**排前面**——一个"排除"操作把病往上推，比没做还糟。

`DENY_FACTOR` 常量和它那 8 行注释一并删掉，方法 javadoc 改写成完整的「为什么打对折是错的」论证。**这个坑要写进代码，不能只写进 commit message**——commit 会被人 `--grep` 不到，代码注释会在下一次有人想"优化"这里时挡一下。

### 20.7 清零而不是删除候选

清零后，仅靠被否认症状才进候选的病会掉到列表最后，但**仍在列表里**。

这是刻意的取舍：

- 误删一个可能正确的病，用户看到的是「系统没提这个」，很难发现，也就很难纠正；
- 排在最后一行，用户和专业医生都能看见，而且下一轮补充信息后它自然会上来。

**排序错了可以修正，从列表里消失就再也回不来了。**

### 20.8 顺带挖出的死代码：`DENY_FACTOR` 本来永远不会触发

改完发现第二层问题：`GraphRetrievalService` 查边的时候只传了**承认的**症状 ID：

```java
var edges = diseaseSymptomMapper.selectEdgesBySymptoms(ids);   // ids 只含 hits
```

被否认的症状边**根本没从数据库查出来**，`denied.contains(edge.getSymptomId())` 永远是 false。

修法是把否认的 ID 也并进去查，但**权重表仍只用承认的**（`idfOf(ids)`）——因为 df 统计的是"本轮命中的症状"，把否认的算进去会污染分母：

```java
var queryIds = new ArrayList<Integer>(ids);
for (var deniedId : deniedIds) {
    if (!queryIds.contains(deniedId)) {
        queryIds.add(deniedId);
    }
}
var edges = diseaseSymptomMapper.selectEdgesBySymptoms(queryIds);
var ranked = DiseaseScorer.score(edges, idfOf(ids), deniedIds, TOP_K);
```

**这类"改了却不可能生效"的 bug，单测和评测都抓不到**——因为两边都只验证输入输出，不验证"这条分支到底跑没跑过"。只有对照实验能抓。

### 20.9 端到端实测

输入：`咳嗽三天了，嗓子有点干，但是我没有发烧，也不头疼`

后端日志（真实输出）：

```
SymptomNormalizer - 症状归一：咳嗽三天了，嗓子有点干，但是我没有发烧，也不头疼
                    → 命中 [咳嗽=咳嗽]，否认 [发烧=发热, 头疼=头痛]
GraphRetrievalService - 图谱检索命中：症状=1，否认=2，疾病=3，追问=2
```

`start` 帧：`sources=["病毒性感冒","风寒感冒","扁桃体炎"]`、`suggestDept=["呼吸内科","内科"]`、`triageSeverity=1`。

模型回复原文：

> 明白了，咳嗽已经三天，嗓子干，**但没有发烧和头痛，这帮我们排除了一些情况**。
>
> 接下来想确认两个关键点：
> 1. 咳嗽是干咳为主，还是有痰？如果有痰，颜色是白、黄，还是带点绿？
> 2. 这几天有没有怕冷、特别想穿厚衣服或盖被子（也就是"恶寒"）的感觉？

三件事同时成立，才算这一步真的生效：

1. 模型**复述了**"没有发烧和头痛"（说明 `【患者明确否认的症状】` 段进了上下文）；
2. 模型**没有反问**发烧或头痛（说明追问层跳过了已回答的症状）；
3. 追问换成了两个新的、有区分度的点（干咳/有痰、恶寒）——**换个角度确认**，而不是原地纠缠。

### 20.11 诚实账

- **清零后指标依旧一动不动。** 原因：现有 35 条用例里没有一条是"仅靠被否认的症状独占候选"的。否认机制的价值在于**防止颠倒事实**，不在于提分。真要度量它，得单独建"否认场景集"（同一主诉 + 否认不同症状，看排序翻转对不对）——这比往主评测集里塞用例更准。
- **`SymptomNormalizerTest` 新增的 3 条一开始是错的**：用例里直接插了 `symptom("发热")` 却用输入"没有发烧"，而"发烧"→"发热"的别名只在 `seed-knowledge.sql` 里有，测试库里没有，归一化命中 0 条，`denied` 永远为空。修法是补一个 `alias(...)` 辅助方法显式建别名。**测试自己也会写错，绿了不代表测到了。**
- **`denialChangesRanking` 最初写成「发热咽痛，但没有发烧」**——同一症状既承认又否认，按"承认优先"规则否认被清空，用例自相矛盾。改成「咽痛，但没有发烧」。
- ~~**症状组合（AND/OR 分组）还没做。**~~ 原担心「同一病的多条近义边累加 = 同一件临床事实被数了三次」。第 21 章用诊断实验证伪了这个猜想，**这条不是我该改的地方**，见 21.2。
- **否认可信度没有分级。** "没有发烧"和"应该没发烧吧"现在同等对待，实际上后者不该清零。要分级就得引入置信度词表，代价是又一层词表要维护。

## 21. 虚词打断：一个被数据否掉的原计划（2026-11-10）

这一章记的是一次**方向修正**。上一章结尾我给自己留的任务是「症状组合（AND/OR 分组）」，理由是同一病的多条近义边累加会让「同一件临床事实被数三次」。写完诊断实验之后，这个理由被证伪了——真正的缺口在别处。把它记下来，是因为「想清楚才动手」比「动手了再解释」便宜得多。

### 21.1 开工前的怀疑

原文案的例子是：一个把「鼻塞/流涕/打喷嚏」都列上的病，患者只说了句"鼻子堵、流鼻涕"，就能靠三条近义边叠出 2.x 分。

但现有打分本身就是 OR 语义——命中任意一条边就得分，多条边是加权求和。这在临床上其实是对的：一个病同时具备三个症状，比只具备一个更可能是它。所以我先怀疑：**这个"缺陷"是不是根本不值得改？** 上一步「排除症状」已经吃过一次亏——实现看着完成、控制实验一跑指标纹丝不动，最后靠诚实记账才承认它是防御性而非提分性改动。

那就先测，别先写。

### 21.2 诊断实验：把每条边按部位摊开

新建了一个一次性的 `BodyPartDiagnosticTest`（跑完就删，类注释里写明了），用真 H2 灌 `seed.sql` + `seed-knowledge.sql`，对 35 条评测用例逐条打印：

- 归一化命中了哪些症状、哪些被否认
- Top3 的病名与分数
- 每一条命中的边按 `symptom.body_part` 分组（`鼻部 鼻塞(0.80) + 流涕(0.80) + 打喷嚏(0.80)`，被否认的标 `✗否认`）

报表落在 `target/body-part-diagnostic.txt`（352 行）。结论很干脆：

**没有任何一条用例是因为「同一部位多症状叠加」而排错的。**

- c01 病毒性感冒靠鼻塞+流涕+打喷嚏叠到 5.843 分排第一 —— **这条本来就该排第一**，叠分是正确表现
- c05 骨折 6.762、c10 风寒感冒 7.871 —— 同样是正确方向
- 如果叠分真的有害，应该看到「某个只命中一条边的病被三边叠加的病挤下去，且被挤下去的才是期望」，一条都没有

原计划被数据否掉了。这是第二次验证同一个方法论：**指标不动的时候，先别加代码，先证明缺口在哪。**

### 21.3 真正的缺口：虚词把最长匹配打断了

报表里 4 条失败用例，根因完全相同：

| 用例 | 实际归一命中 | 期望 | 为什么 |
|---|---|---|---|
| c08「嘴里长了个溃疡，疼得吃不下饭」 | 只有 `食欲减退←吃不下`，榜首是**胃溃疡** 1.623 | 口腔溃疡 | 别名「嘴里溃疡」被「长了**个**」打断 |
| c18「脚踝扭了，肿得老高，一碰就疼」 | **无命中**，召回空 | 骨折 | 「肿**得**老高」根本没有别名 |
| c29「嗓子里有脓点，发高烧」 | 只有 `发热←发高烧`，病毒性感冒与扁桃体炎**同分 1.207** | 扁桃体炎 | 别名「嗓子有脓」被「嗓子**里**有脓点」打断 |
| c31「吐了一口血，大便发黑」 | `呕吐←吐了` + `黑便`，榜首**偏头痛** 1.623 | 胃溃疡 | 别名「吐血」被「吐**了一口**血」打断，反而命中了更短的「吐了」→ 呕吐 |

这是两种不同的病，得分开治：

- **c18 是别名覆盖缺口**。「局部肿胀」四个字在「肿得老高」里一个都不连续出现，中间隔着「得」，而「局部」根本没说——松散匹配也救不了，只能补别名。
- **c08/c29/c31 是归一化能力缺口**。别名本身是对的，是患者在中间插了「长了个」「里」「了一口」这种虚词。

### 21.4 改在归一化层，不是打分层

`SymptomNormalizer` 新增松散匹配，三条约束：

1. **最多夹 3 个字**（`MAX_GAP = 3`）。实测里最长的干扰是「长了个」「了一口」这种三字插入。放到 5 会开始把不相干的两句拼起来。
2. **两字词只允许夹 2 个字**（`token.length() == 2 ? 2 : MAX_GAP`）。「发热」如果也允许夹 3 个字，就会被松成「发现很热」这种无语义关联。
3. **夹字的内容必须在白名单里**：

```java
private static final String GAP_ALLOWED =
        "了着过得的地个只些点儿一两三四几半里外上下中内前后边"
                + "是有很太都也还就又再才刚一直点儿种样么之其该把被让给对从向于"
                + "长出起";
```

**为什么是白名单而不是黑名单**：黑名单挡不住想象不到的组合。先排除掉否定词，剩下的字符里「发热」仍会被松成「发现很热」、「吐血」会被松成「吐出来的血块」——都是把不相干的词连起来，而且是那种"看起来很像"的错误，比漏召更难发现。白名单只放真正的中文虚词、量词、数词，宁可漏几个说法，也不制造假匹配。

**否定词（不没无未否别非）故意不在白名单里**，这样「嗓子不疼」永远不会被松成「嗓子疼」。漏召一个症状可以靠补别名解决；把患者主动排除的症状记成他有，是**颠倒事实**。

### 21.5 一个必须做对、否则整段白写的细节

松散匹配**必须和精确匹配在同一轮循环里**做：

```java
for (var row : vocabulary) {
    var token = row.getMatchText();
    if (token == null || token.isEmpty()) continue;
    boolean matchedExactly = matchExact(text, token, taken, row, hits, denied);
    if (!matchedExactly) matchLoose(text, token, taken, row, hits, denied);
}
```

不能拆成两遍（先全部精确、再全部松散）。原因在 `boolean[] taken` 这个位置占位数组上：

「吐了一口血」里，短别名「吐了」会先精确命中并占住「吐」这个位置；轮到长别名「吐血」时，`overlaps(taken, ...)` 直接把它挡回。而「吐了」是**错的那条**（患者不是在呕吐，是在吐血）。

拆两遍的话这个错误永远修不掉。同一轮里做，就不需要撤销已经写进 `taken` 的占位——因为长词也只是"没精确命中"才退松散，它本来就没写进去。

另外 `matchedText` 传的是**原文切片**（`text.substring(idx, spanEnd)`），不是别名本身。这样下游 `formatGraph` 回显患者原话时显示的是「嘴里长了个溃疡」，而不是硬邦邦的「口腔溃疡」。

### 21.6 两次控制实验：证明它真的生效

上次栽在「写了个测不出效果的改动」上，这次一开始就设计好对照组。

补别名 + 开松散后，评测：

```
EVAL cases=35 有期望=30 无期望=5 | Recall@3=100.0% (30/30) | MRR=0.983
     | 科室一致=100.0% (30/30) | 红旗=7/7 | 误报=0/5
```

但这不足以说明是**松散匹配**的功劳——别名也补了。于是做两组对照：

| 实验 | Recall@3 | MRR | 科室一致 | 说明 |
|---|---|---|---|---|
| 只开松散 + 补别名 | 100.0% (30/30) | 0.983 | 100.0% (30/30) | 最终态 |
| **关掉松散** + 补别名 | 96.7% (29/30) | 0.933 | 93.3% (28/30) | 别名贡献 29/30，松散再补 1 条（c08） |
| **关掉松散** + 不补别名 | 93.3% (28/30) | 0.900 | 90.0% (27/30) | 这是改动前的基线 |

两组对照把两条改动的贡献分离干净了：别名补上 1 条（c18）、松散再补 1 条（c08），两个都要有才到 100%。

### 21.7 c08 卡住的那半小时

c08 在「开着松散、别的都对了」的状态下仍然失败，一度以为松散没生效。实际原因是：前缀「嘴里」和后缀「溃疡」都对，中间夹了「长了个」三个字，字数和位置都符合——**卡在「长」这个字不在 `GAP_ALLOWED` 白名单里**。

这跟"夹几个字"是完全不同的问题，是**夹字的内容**问题。白名单里补上「长出起」之后 c08 立刻修好。

教训：白名单一旦选了，每次漏召都要问一句「是词表不够，还是字表不够」，这两个坑长得一模一样。

### 21.9 端到端实测

单测跑的是 H2，真库是 MySQL，中间还有「seed 文件改了但库没重灌」这道坎——必须真打一次。

`_verify_loose.py` 对四条用例各建一个问诊单、发一句话、只取 SSE 首帧的 `sources` / `suggestDept`，然后取消并删除：

| 用例 | 主诉 | 首帧 `sources` | 首帧 `suggestDept` | 命中 |
|---|---|---|---|---|
| c08 | 嘴里长了个溃疡，疼得吃不下饭 | `["口腔溃疡", "胃溃疡"]` | `["口腔科"]` | ✅ |
| c18 | 脚踝扭了，肿得老高，一碰就疼 | `["骨折"]` | `["外科"]` | ✅ |
| c29 | 嗓子里有脓点，发高烧 | `["扁桃体炎", "病毒性感冒", "风寒感冒"]` | `["呼吸内科"]` | ✅ |
| c31 | 吐了一口血，大便发黑 | `["偏头痛", "胃溃疡"]` | `["急诊科"]` | ✅ |

**第一次跑 c18 还是空的。** 原因不是代码——`seed-knowledge.sql` 里补的 5 条「局部肿胀」别名只改了文件，**没有在真 MySQL 上重放**。`SELECT COUNT(*) FROM symptom_alias WHERE symptom_id = 27` 返回 2，文件里是 5。补执行之后 c18 立刻变成 `["骨折"]`。

这个坑值得单独记一句：`seed-knowledge.sql` 是**手工执行**的数据脚本（不进 Flyway，结构归迁移、数据归人），改完文件不等于库里有。重灌之后还要重启进程，因为词表有 5 分钟 TTL 缓存。

### 21.10 已知边界

- **c31 的 Top1 仍然是偏头痛**。原因：「吐了一口血」经松散匹配命中「呕吐」，而偏头痛的症状表里挂着呕吐边。要修得靠"出血类症状的权重压制"或者给呕吐加排除条件（呕血≠呕吐），不是松散匹配能解决的。**`sources` 里胃溃疡已经在第 2 位，模型拿得到，所以端到端是可用的**——但排序上这里确实还欠一次。
- **白名单是手写的，没有从语料统计出来**。更严谨的做法是拿一批真实主诉做字频统计，取高频虚词。现在是按「中文虚词/量词/数词」的直觉列的，够用但不完备。
- **`GAP_ALLOWED` 和 `MAX_GAP` 是两个耦合参数**。放宽任一个都可能引入假匹配，改动时必须跑控制实验，不能只看主指标涨没涨。
- **评测集仍然只有 35 条**，且几乎都是「一句话主诉」。多轮对话里的顺序信息、时间信息（"从昨天开始"）都还没进评测。
